# THI-104 — Interact with Claude Code prompts from the UI

**Linear:** [THI-104](https://linear.app/thibault-dody/issue/THI-104/allow-for-interaction-with-claude-code-when-being-prompt)
**Date:** 2026-05-14
**Status:** Design approved

## Summary

When a Claude Code agent pane is waiting on an interactive prompt, Switchboard
should surface that prompt as structured UI inside the terminal modal and let
the user answer it — navigate with ↑/↓ and confirm with Enter — without having
to read the raw terminal output.

## Goals

- Detect Claude Code's modern numbered "arrow-key menu" prompts and render them
  as a structured choice list.
- Also handle legacy `(y/n)` prompts and `press enter` / `continue?` prompts.
- Let the user answer the prompt from the terminal modal: ↑/↓ to move, Enter to
  confirm, mouse click to jump to a choice.
- Keep the rendered state an honest mirror of the real pane — what the user sees
  is what Claude sees.

## Non-goals

- Surfacing prompt choices on window cards or in the NeedsStrip. This ticket is
  scoped to the terminal modal only. The parser is built to be reusable so a
  future card-level feature can pick it up, but no card/NeedsStrip UI ships here.
- Adding prompt data to the `/api/state` response or the `Agent`/`Window`
  schema. Prompt data travels only over the per-pane WebSocket.
- Changing the global state poll cadence (that is sibling ticket THI-105).
- Free-text follow-up interaction (typing a response to Claude from the UI).
  Descoped during planning to **THI-112** — Claude's input box cannot be
  distinguished from plain idle state in a single pane capture, so it needs its
  own design.

## Approach

**Parse inside the WebSocket stream.** The `PaneStreamer` already captures the
pane content for the open terminal modal. It additionally runs prompt-detection
on each capture and pushes a small JSON control message over the *same*
WebSocket the modal already listens on. The modal renders an overlay from it.

This was chosen over two alternatives:

- *Dedicated `/api/prompt` polling endpoint* — adds a second poll loop competing
  with the WS stream and conceptually overlaps with THI-105.
- *Piggyback on `/api/state`* — ties prompt freshness to the global poll cadence
  (~1–2s), so the highlight would lag badly behind live arrow presses.

Parsing in the stream is the only option that makes "arrows forwarded live,
highlight mirrors the cursor" feel live, and it stays cleanly scoped to the
modal.

## Backend

### Shared prompt parser

Refactor the prompt-detection logic out of `claude_parser._scan_pending` into a
standalone, well-tested function:

```python
def parse_prompt(lines: list[str]) -> Prompt | None
```

It scans the pane tail and classifies into one of three `kind`s:

- `menu` — Claude Code's modern numbered menu. Detect a cluster of
  `^\s*[❯>]?\s*\d+\.\s+…` lines (tolerant of leading box-drawing characters);
  the line bearing the `❯` cursor marker is `selected`. The non-empty line(s)
  directly above the first choice become `question`.
- `yn` — legacy `(y/n)` / `[y/n]` (existing regexes).
- `enter` — `press enter` / `continue?` (existing regexes).

`parse_pane` keeps returning its `pending_input` bool for the card path, but now
derives it as `parse_prompt(lines) is not None` — one source of truth, no
duplicated regex logic.

### Schema

New Pydantic models in `schemas.py`:

```python
class PromptChoice(_CamelModel):
    index: int        # 1-based, as Claude Code numbers them
    label: str
    selected: bool    # the choice currently bearing the ❯ cursor

class Prompt(_CamelModel):
    kind: Literal["menu", "yn", "enter"]
    question: str | None
    choices: list[PromptChoice]   # [] for "enter"
```

These are **not** added to the `Agent`/`Window` schema — they travel only over
the WebSocket.

### WS stream integration

`PaneStreamer` runs `parse_prompt` after each capture (both the initial snapshot
and the FIFO-fallback poll path) and, **when the result changes**, sends a JSON
control message on the existing WS:

```json
{ "type": "prompt", "prompt": { … } | null }
```

Raw terminal bytes continue to flow as binary frames exactly as today; the modal
already distinguishes text/JSON from binary.

For the low-latency FIFO path (which streams raw bytes, not full captures), the
streamer adds a lightweight re-capture-and-parse on a short timer (~150ms)
**only while a prompt is active or just cleared**, so the highlight tracks live
arrow presses without re-capturing constantly when nothing is happening.

The streamer only runs `parse_prompt` for panes whose `kind == "agent"` — the
same gate `collect_state` already uses.

No new HTTP endpoint. No change to `/api/send` or `/api/state`.

## Frontend

### New component: `PromptOverlay.tsx`

Rendered inside `TerminalModal`, docked as a panel **between the xterm host and
the footer** — visible only when a prompt is active, and deliberately *not*
covering the terminal so the user keeps full context. `Prompt`/`PromptChoice`
types are added to `types.ts`.

### Modal wiring

`TerminalModal` gains a `prompt` state. Its WS `onmessage` handler — which
already separates text/JSON from binary — also handles `{type:"prompt"}` →
sets/clears `prompt`. When `prompt` becomes non-null, focus moves to the overlay
(so arrows hit the overlay handler, not xterm — avoids double-send); when it
clears, focus returns to xterm.

### Per-kind interaction

All keys are sent over the existing WS using the protocol already in place
(`{"signal":"…"}` → `tmux.send_signal`; plain text → literal paste).

| `kind` | Render | Interaction |
|--------|--------|-------------|
| `menu` | Vertical choice list; the parsed `selected` choice highlighted (accent + `❯`). Hint: "↑↓ move · Enter confirm". | ↑/↓ keys → `{"signal":"Up"/"Down"}` forwarded live. **Click a choice** → compute delta from the current `selected` index, send that many Up/Down signals, *no commit*. **Enter** (key or Submit button) → `{"signal":"Enter"}`. |
| `yn` | Yes / No buttons. | Click/key → literal `y` or `n` (no Enter — matches Claude's immediate y/n behavior; see Risks). |
| `enter` | Single "Continue" button. | → `{"signal":"Enter"}`. |

### Highlight is a mirror, not optimistic

The highlighted choice always reflects the *last parsed* `selected` from the
backend. Pressing ↑ shows a ~150ms lag before the highlight moves — this is
intentional and honest: it mirrors the real pane cursor, so what the user sees
is what Claude sees. No local prediction state to drift out of sync.

### Esc stays "close modal"

The overlay does not hijack Esc. To cancel/decline a menu, the user navigates to
the decline choice (Claude Code always offers one). This avoids ambiguity
between "close the modal" and "cancel the prompt."

### New files

- `components/PromptOverlay.tsx` — the overlay component.
- `lib/prompt.ts` — `Prompt`/`PromptChoice` types and the arrow-delta helper
  (unit-testable in isolation).

## Edge cases & error handling

1. **Mid-redraw mis-parse.** Claude Code redraws its menu box; a capture can
   land mid-frame. `parse_prompt` returns a `menu` only if it finds ≥1 numbered
   choice. Zero choices → return `null` (treated as "no prompt") rather than a
   broken overlay. Zero cursor markers → valid menu, highlight nothing; exactly
   one → highlight it; more than one → take the last. When the selection is
   unknown, click-to-jump is disabled (no delta to compute) — keyboard ↑/↓ still
   works.
2. **Prompt vanishes between render and action.** The streamer emits
   `{type:"prompt", prompt:null}` the moment detection clears, so the overlay
   disappears promptly. A small race window remains (commit just as it clears) —
   accepted: keys go to the pane regardless, worst case a stray `Up` in a shell.
3. **Non-agent panes.** A plain shell can echo `(y/n)`. The streamer only runs
   `parse_prompt` for panes with `kind == "agent"`. No overlays on shell panes.
4. **WS reconnect mid-prompt.** The streamer parses on its initial snapshot too,
   so a reconnect re-emits the `{type:"prompt"}` message and the overlay
   reappears. No extra handling.
5. **Double-send from xterm.** While the overlay is active it owns `keydown` for
   ↑/↓/Enter (`preventDefault` + `stopPropagation`) and xterm's textarea is
   blurred — so a key is never sent twice.
6. **Commit mashing.** Enter is debounced (~300ms) so mashing it cannot blow
   through onto the next prompt.
7. **Re-parse cost.** The ~150ms timed re-capture runs only while a prompt is
   active (plus a short tail after it clears). When idle, parsing piggybacks on
   captures that already happen.

## Risks

- **`yn` may need a trailing Enter.** We send the bare `y`/`n` char (matches
  Claude's immediate-react behavior). If some prompt needs a trailing Enter, the
  fix is one line — documented, not pre-solved.

  capture with a menu emits one `{type:"prompt"}` message; clearing emits
