# THI-117 — Terminal WebSocket auto-reconnect with xterm state preservation

**Linear:** [THI-117](https://linear.app/thibault-dody/issue/THI-117/terminal-websocket-auto-reconnect-with-xterm-state-preservation)
**Date:** 2026-05-18
**Status:** Design approved

## Summary

When the `/ws/pane` connection drops today, `TerminalModal` flips its pill to
`closed` and does nothing — the user has to close and reopen the modal to get
a live stream back. Port periscope's auto-reconnect behavior so the modal:

1. Reopens the socket on its own with exponential backoff
   (`250 → 500 → 1000 → 2000 → 4000 → 4000 → 4000 → 4000` ms).
2. Preserves the xterm.js Terminal instance across reconnect attempts
   (scrollback above the visible viewport stays put until manually cleared).
3. Writes `[reconnecting…]` (yellow) into the pane buffer once per disconnect
   sequence and `[reconnected]` (green) on the first successful re-open.
4. Caps at 8 retries after the initial failure (sum of the backoff array =
   ~19.75 s of trying), then transitions to a `disconnected` state with a
   manual **Reconnect** button in the modal footer.
5. Differentiates permanent failures (pane gone) from transient blips via
   WebSocket close codes — a `4404` / `4410` close skips the backoff and
   transitions straight to a terminal `gone` state.

## Background

`TerminalModal.tsx`'s connection lifecycle currently lives inside the same
`useEffect` that constructs the xterm Terminal. `ws.onclose` and `ws.onerror`
only call `setConn("closed")` — there is no recovery path. The terminal is
also disposed on every effect cleanup, so even a hypothetical reconnect that
reused the effect would lose scrollback.

The `routers/ws.py` handler already closes with code `4404` when the pane
doesn't exist at accept time. There is no close code emitted for the case
where the stream ends after a successful connect (e.g. tmux kills the pane
mid-session): the `pane_stream` task returns silently and the main receive
loop sits in a zombie state until the client gives up.

Periscope's reference implementation lives at `~/github/periscope/static/terminal.js`
(~L130-200). It uses the same backoff curve, writes notices in the buffer, but
retries forever — Switchboard caps the loop and adds an explicit "Reconnect"
affordance.

## Non-goals

- **Server-side replay buffer.** Each reconnect re-runs
  `pane_stream.PaneStreamer.run()`, which sends a fresh `capture_pane(500)`
  snapshot. There is no per-pane ring buffer of bytes streamed since the last
  connect. A future ticket can layer delta-replay on top if needed.
- **Local keystroke buffering during disconnect.** The existing
  `term.onData → ws.send` path already drops keystrokes when the socket is not
  `OPEN`; that behavior is preserved.
- **Auto-resize syncing during reconnect.** The existing `sendSize()` already
  fires on `ws.onopen`, so the post-reconnect socket reports the current
  modal size as its first message — no special path needed.
- **Reconnect on `wsStreamEnabled=false`.** Snapshot mode does not open a
  WebSocket, so there is nothing to reconnect.
- Any change to non-`/ws/pane` sockets. This ticket scopes to the terminal
  modal's pane stream.

## Architecture

```
                            ┌─────────┐
                  open ───►│  live   │◄─── successful reconnect
                  ↑         └────┬────┘
                  │              │ ws.onclose (non-permanent)
            ┌─────┴──────┐       ▼
   start ──►│ connecting │  ┌──────────────┐
            └────────────┘  │ reconnecting │──► backoff timer
                            └──────┬───────┘
                                   │ all attempts exhausted
                                   ▼
                            ┌────────────────────────────┐
                            │ disconnected (manual btn)  │
                            └────────────────────────────┘

  4404 / 4410 close at any point  →  ┌───────────┐
                                     │   gone    │  (terminal; no retry)
                                     └───────────┘
```

The `Connection` type in `TerminalModal.tsx` expands from 4 values to 6:

| State | Meaning | Pill text | Reconnect button? |
|---|---|---|---|
| `connecting` | initial socket attempt | `connecting` | no |
| `live` | open WS, streaming | `WS · live` | no |
| `reconnecting` | backoff loop active | `reconnecting · N/8` | no |
| `disconnected` | cap exhausted, awaiting user | `disconnected` | **yes** |
| `gone` | server signaled pane no longer exists | `pane gone` | no |
| `snapshot` | live streaming disabled in settings | `snapshot` | no |

Three new component refs hold reconnect controller state:

```ts
attemptRef:        useRef(0)            // index into BACKOFF_MS
intentionalRef:    useRef(false)        // true while teardown is in progress
backoffTimerRef:   useRef<number|null>  // active setTimeout id
noticeWrittenRef:  useRef(false)        // [reconnecting…] sent once per disconnect run
```

## Frontend — `lib/wsReconnect.ts` (new)

Extract policy decisions into a pure module so they can be tested without
xterm or WebSocket mocks. The module exports:

```ts
export const BACKOFF_MS = [250, 500, 1000, 2000, 4000, 4000, 4000, 4000];

export type CloseAction =
  | { kind: "ignore" }                              // intentional / stale
  | { kind: "gone" }                                // 4404 / 4410
  | { kind: "retry"; delayMs: number; attempt: number }
  | { kind: "exhausted" };                          // cap reached

export function decideCloseAction(
  closeCode: number,
  attempt: number,
  isIntentional: boolean,
  isStale: boolean,
): CloseAction;
```

Decision table:

| Inputs | Output |
|---|---|
| `isIntentional` or `isStale` | `ignore` |
| `closeCode ∈ {4404, 4410}` | `gone` |
| `closeCode === 1000` | `ignore` |
| `attempt >= BACKOFF_MS.length` | `exhausted` |
| otherwise | `retry` with `delayMs = BACKOFF_MS[attempt]` |

## Frontend — `TerminalModal.tsx` (refactor)

The construction `useEffect` currently builds the Terminal *and* opens the
WS in the same scope. Reconnect needs the Terminal to outlive the socket,
so the WS opening moves into a `connect(isReconnect)` closure that the
effect calls once at mount and that calls itself via `setTimeout` on each
backoff tick.

```ts
function connect(isReconnect: boolean) {
  if (isReconnect) term.clear();
  setConn(isReconnect ? "reconnecting" : "connecting");
  const ws = openPaneWS(win.session, win.index);
  wsRef.current = ws;

  ws.onopen = () => {
    if (attemptRef.current > 0) {
      term.writeln("\r\n\x1b[32m[reconnected]\x1b[0m");
    }
    attemptRef.current = 0;
    noticeWrittenRef.current = false;
    setConn("live");
    sendSize();
  };

  ws.onmessage = /* unchanged from today */;
  ws.onerror   = () => { /* onclose follows; no-op */ };

  ws.onclose = (e) => {
    const action = decideCloseAction(
      e.code,
      attemptRef.current,
      intentionalRef.current,
      ws !== wsRef.current,
    );
    switch (action.kind) {
      case "ignore":   return;
      case "gone":
        term.writeln("\r\n\x1b[31m[pane no longer exists]\x1b[0m");
        setConn("gone");
        return;
      case "exhausted":
        setConn("disconnected");
        return;
      case "retry":
        if (!noticeWrittenRef.current) {
          term.writeln("\r\n\x1b[33m[reconnecting…]\x1b[0m");
          noticeWrittenRef.current = true;
        }
        setConn("reconnecting");
        attemptRef.current = action.attempt + 1;
        backoffTimerRef.current = window.setTimeout(
          () => connect(true),
          action.delayMs,
        );
        return;
    }
  };
}
```

**`term.onData → wsRef.current.send` moves outside `connect()`** so it
survives reconnects. Today the closure binds to `sock` inside the effect
(line 252), which works only because `wsRef` is never replaced. After this
change, every keystroke reads the current socket from the ref. This is a
small correctness fix that ships with the reconnect work, not a separate
refactor.

**Cleanup function additions:**

```ts
return () => {
  intentionalRef.current = true;
  if (backoffTimerRef.current) window.clearTimeout(backoffTimerRef.current);
  // ... existing cleanup unchanged
};
```

**Manual reconnect button** renders in the footer when `conn === "disconnected"`,
between the connection pill and the cwd:

```ts
const manualReconnect = () => {
  attemptRef.current = 0;
  noticeWrittenRef.current = false;
  connect(true);
};
```

The button is a single `<button className="btn btn-ghost">Reconnect</button>`;
no new CSS class needed beyond what `.term-foot` already provides.

## Backend — `routers/ws.py`

The current handler runs the streamer task fire-and-forget and only the
client-receive loop can exit the main `try`. If the streamer task completes
on its own (FIFO writer closed because tmux killed the pane, pipe-pane
failed, etc.), the socket sits open with no further data — a zombie state.

**Restructure to race the two tasks** with `asyncio.wait(..., FIRST_COMPLETED)`:

```python
# Extract the existing while-True recv body into a helper.
async def _pane_recv_loop(
    ws: WebSocket,
    session: str,
    index: int,
    saved_size_box: list,  # mutable holder for restore_window_size
) -> None:
    while True:
        msg = await ws.receive_text()
        # ... existing json/keys dispatch unchanged

# In pane_socket(), replace the current try/finally body:
saved_size_box: list = [None]
recv_task = asyncio.create_task(_pane_recv_loop(ws, session, index, saved_size_box))
try:
    done, _pending = await asyncio.wait(
        [tail_task, recv_task],
        return_when=asyncio.FIRST_COMPLETED,
    )
    if tail_task in done and recv_task not in done:
        with contextlib.suppress(Exception):
            await ws.close(code=4410, reason="pane stream ended")
        recv_task.cancel()
        with contextlib.suppress(asyncio.CancelledError, Exception):
            await recv_task
    else:
        tail_task.cancel()
        with contextlib.suppress(asyncio.CancelledError, Exception):
            await tail_task
except WebSocketDisconnect:
    pass
finally:
    # saved_size restore + active-streamer deregister unchanged
    ...
```

**Close codes after this change:**

| Code | Source | Meaning |
|---|---|---|
| `4404` | `pane_socket` accept-check | Pane doesn't exist at connect time. (Unchanged.) |
| `4410` | `pane_socket` post-race | Stream ended while client was still connected. (**New**.) |
| `1000` | normal close | Default for clean WS shutdown. |
| `1006` | abnormal | TCP reset, server killed, uvicorn `--reload`. |

The frontend treats `4404` and `4410` identically, but keeping them distinct
makes server-side logs unambiguous about which gate fired.

**No changes to `services/pane_stream.py`.** Every reconnect produces a fresh
`PaneStreamer.run()`, which already emits a fresh snapshot. The per-target
streamer eviction (THI-116) cleanly hands the pane from the old connection's
pipe-pane to the new one's.

## Testing

**Frontend — `lib/wsReconnect.test.ts`** (pure, fast):
- `1006` close at attempts 0..7 → `retry` with the right delay
- `1006` close at attempt 8 → `exhausted`
- `4404` / `4410` close, any attempt → `gone`
- `1000` close → `ignore`
- `isIntentional = true` → `ignore`
- `isStale = true` → `ignore`

**Frontend — `TerminalModal.test.tsx`** (integration, using `vi.useFakeTimers`
and a mock `openPaneWS` factory):
- `onclose({code: 1006})` writes `[reconnecting…]` once and schedules
  `setTimeout` with `BACKOFF_MS[0]`
- Three consecutive 1006 closes write `[reconnecting…]` only once
  (then `[reconnected]` only once on success)
- `onclose({code: 4404})` writes `[pane no longer exists]` and renders
  the "pane gone" pill; no `setTimeout` scheduled
- Exhausting the backoff array renders the "Reconnect" button; clicking it
  resets `attemptRef` and re-enters the cycle
- Unmount during `reconnecting` calls `clearTimeout` on the active timer
  (assert via `vi.useFakeTimers` + spy)

**Backend — `tests/test_ws.py`** (extend):
- Streamer task completes while recv loop is still active → handler emits
  `ws.close(code=4410, ...)`
- Client disconnects (recv task raises `WebSocketDisconnect`) → no `4410`
  emitted; `tail_task` cancelled cleanly
- `saved_size` restore is called exactly once regardless of which task
  completes first (use a stub that records calls)
- Existing 4404 accept-time test stays green

**Manual test plan (for PR body):**

- Restart uvicorn (`pkill -f 'uvicorn switchboard'` then `./scripts/dev.sh`)
  → modal shows `[reconnecting…]`, then `[reconnected]`; scrollback is
  clean (no duplicate snapshot).
- `tmux kill-window` on the open pane → modal shows
  `[pane no longer exists]`, no retry, no Reconnect button.
- DevTools → Network → Offline for ~5 s, then back online → reconnect
  succeeds within one backoff cycle.
- DevTools → Network → Offline indefinitely → after ~20 s pill flips to
  `disconnected`, Reconnect button appears; clicking it cycles through the
  backoff array again and re-shows the button on failure.
- Close modal during the reconnecting state → no console errors, no orphan
  timers.
- Toggle `wsStreamEnabled` to false during reconnect → modal flips to
  `snapshot` cleanly; toggling back re-opens a live socket.

## Open questions / future work

- **Delta-replay** (server-side ring buffer keyed by a session-resume token)
  is the obvious next layer if reconnects become frequent and the
  re-snapshot cost becomes annoying. Out of scope.
- **Pause/resume cap** — if the user backgrounds the tab for an hour, the
  browser will eventually fire `onclose` on the idle socket. The current
  cap (8 attempts ≈ 16 s) will give up before the user notices. Could be
  addressed later by listening for `visibilitychange` and resetting
  `attemptRef` on tab focus. Deliberately not in this ticket.
